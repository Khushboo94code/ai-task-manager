# AI Task Manager

A full-stack task management system with an agentic AI assistant that can create, update, and query tasks using natural language, backed by a retrieval-augmented knowledge base.

---

## Stack

| Layer | Technology |
|---|---|
| Frontend | React 18 + Vite + Tailwind CSS |
| Backend | Python 3.11 + FastAPI |
| LLM | OpenAI GPT-4o-mini |
| Retrieval | TF-IDF with synonym expansion (no embeddings) |
| Storage | In-memory (module-level Python lists/dicts) |

---

## Features

### Task Management (Part A)

- Create, read, update, and delete tasks via REST API or the AI assistant
- Fields: title (required), description (optional), status (`pending` / `in_progress` / `completed`), priority (`low` / `medium` / `high`), due date
- Status filter tabs and debounced full-text search
- Overdue detection (red badge on cards past their due date)
- Dark mode toggle with localStorage persistence

### AI Assistant (Part B)

- Natural language interface in a side panel
- Two-call agentic loop: first call decides which tools to use; second call incorporates tool results into the final answer
- Session-based conversation history (backend in-memory, 30-minute TTL, max 20 turns)
- Delete confirmation flow: destructive actions require explicit "Confirm Delete" before execution
- Idempotency: each send generates a unique key; duplicate requests return the cached result
- Route badge on every assistant response: `Knowledge Base` / `Tool Call` / `KB + Tool` / `Out of scope`
- Evidence chips showing which KB document was cited and its relevance score

### Available Tools

| Tool | Description |
|---|---|
| `list_tasks` | Filter tasks by status, priority, or search query |
| `get_task` | Fetch a single task by ID |
| `create_task` | Create a task (asks for description, priority, due date before calling) |
| `update_task` | Update any field on an existing task |
| `delete_task` | Delete a task (requires confirmation) |

## How Retrieval Works

The knowledge base is a set of Markdown files in `backend/services/retrieval/docs/`:

| Document | Covers |
|---|---|
| `priority_definitions.md` | What high / medium / low priority means |
| `status_lifecycle.md` | When to move tasks between statuses |
| `due_date_overdue_policy.md` | Overdue rules and escalation |
| `deletion_policy.md` | When and how to delete tasks |
| `task_title_guide.md` | How to write good task titles |
| `team_workflow.md` | Sprint and review conventions |

**Algorithm — TF-IDF with synonym expansion:**

1. **Tokenise** the query: lowercase, strip punctuation, expand synonyms.  
   E.g. "ticket urgency" → ["ticket", "task", "job", "urgency", "priority", "importance"] (synonyms injected by `synonyms.py`)
2. **Score** each document using TF-IDF cosine similarity against the query vector.
3. **Filter** — only documents scoring ≥ **0.1** are passed to the LLM. Documents below this threshold are discarded before the prompt is built.
4. **Include scores** in the prompt so the LLM can weight evidence proportionally.

**Why TF-IDF and not embeddings?**  
The KB has 6 short documents — small enough that the scoring is interpretable and the threshold can be reasoned about. An embedding model would add network latency, a vector store dependency, and an API cost for a retrieval corpus this size. TF-IDF with synonym expansion achieves comparable recall on domain vocabulary without any external service.

**Threshold example:**

| Query | Top doc | Score | Passed? |
|---|---|---|---|
| "what does high priority mean?" | `priority_definitions.md` | 0.52 | Yes |
| "create a task for the login bug" | `priority_definitions.md` | 0.08 | No (below 0.1) |
| "when should I mark a task completed?" | `status_lifecycle.md` | 0.38 | Yes |

A query about creating a task scores 0.08 against all KB docs — none are relevant, so the assistant routes to tool-only and the KB is not injected into the prompt.

## Assumptions and Trade-offs

| Decision | Why |
|---|---|
| In-memory storage | Assignment requirement; tasks reset on server restart |
| Backend session history | Keeps frontend stateless; consistent with in-memory pattern; avoids sending full history on every request |
| Synonym expansion at query time | Handles vocabulary mismatch (task/ticket/job) without reindexing |
| Delete requires confirmation | Destructive operations should be explicit; prevents misidentification from deleting the wrong task |
| Description is optional | Users should not be blocked from creating a task if they want to fill details later |
| Max 20 session turns | Prevents unbounded context growth; old turns are dropped FIFO |
| Port 8001 (not 8000) | Port 8000 was occupied by another process on the development machine |
